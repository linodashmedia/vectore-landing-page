Deployment runbook

Put the Vectore blog on Railway

Nine steps, done once. At the end, WordPress is answering at vectore.io/blog behind the landing page, with the teal theme active and uploads that survive a redeploy.

  • ~20 minutes
  • 2 services + 1 volume
  • order matters

Steps

    0 of 9 done
    01

    Add the database Railway › your existing project › New

    Choose Database → Add MySQL. Put it in the same project as the landing page, not a new one.

    Why the same project: services in one project reach each other over Railway's private network. A database in a separate project would have to be reached over the public internet, which is slower and billed as egress.

    02

    Create the blog service New › GitHub Repo › vectore-landing-page

    Pick the same repository the landing page already uses. Railway will start a build immediately — let it fail, it has nowhere to build from yet.

    Then open Settings → Source and set:

    Root Directory
    blog
    !

    This is the step everything else depends on. The root directory becomes the Docker build context, and every COPY path in the Dockerfile is written relative to blog/.

    Get it wrong and the build fails on the first COPY with a file-not-found, which reads like a missing file rather than a wrong setting.

    No builder to choose: blog/railway.json already declares the Dockerfile and the health check. Railway reads it once the root directory points at it.

    03

    Wire up the database Blog service › Variables › Raw editor

    Paste these exactly as written, braces and all. Railway resolves them at deploy time.

    Blog service variables
    MYSQLHOST=${{MySQL.MYSQLHOST}}
MYSQLPORT=${{MySQL.MYSQLPORT}}
MYSQLUSER=${{MySQL.MYSQLUSER}}
MYSQLPASSWORD=${{MySQL.MYSQLPASSWORD}}
MYSQLDATABASE=${{MySQL.MYSQLDATABASE}}

    Why references, not the actual values: a pasted password keeps working right up until someone rotates the database credentials, and then the site goes down months later with nothing in the diff to explain it. A reference always resolves to the current value.

    Why these names: the WordPress image reads WORDPRESS_DB_*, but Railway publishes MYSQL*. The container's entrypoint maps one to the other on boot, so you set the names Railway already gives you.

          05
          
    Tell WordPress where it lives
            Same Variables panel
          
    
        
    
        
    
          
    
            
    Blog service variables
    

    VECTORE_BLOG_URL=https://vectore.io/blog
VECTORE_SITE_URL=https://vectore.io
VECTORE_WAITLIST_ENDPOINT=https://vectore.io/api/waitlist
    
          
    
          
    The /blog suffix is load-bearing. WordPress genuinely lives at that path inside the container, and this is what it uses to build every link it prints. Setting it as a constant also locks the fields in Settings → General, so nobody can half-move the site by typing a new URL into wp-admin.
    
          
    The waitlist endpoint is where blog newsletter signups get forwarded, so there is one list rather than two. Leave it unset and the form says signups are not configured instead of quietly dropping addresses.
    
        
    
      
    

      
      
    
        
    
          
          06
          
    Add a volume for uploads
            Blog service › Settings › Volumes
          
    
        
    
        
    
          
    Add a volume and set its mount path to:
    
          
    
            
    Mount path
    
            
    /var/www/html/wp-content/uploads
    
          
    
          
    
            !
            
    Do this before publishing anything. The container filesystem is thrown away on every deploy. Without the volume, every image an editor uploads disappears the next time you push — and the posts that referenced them are left with broken images.
    
          
    
          
    Only the uploads need it. The theme is baked into the image and comes back identical every build, so it needs no persistence. The media library is the one thing WordPress writes that you cannot regenerate.
    
        
    
      
    

      
      
    
        
    
          
          07
          
    Point the landing page at it
            Landing page service › Variables
          
    
        
    
        
    
          
    First, on the blog service, open Settings → Networking and copy its private domain — something like blog.railway.internal. Note the port it listens on while you are there.
    
          
    Then, on the landing page service, add:
    
          
    
            
    Landing page variable
    

    BLOG_ORIGIN=http://blog.railway.internal:8080
    
          
    
          
    Substitute the private domain and port you just read. This is the only change the landing page needs.
    
          
    Private, not public: the hop stays inside Railway's network, so it is faster and is not billed as egress. It also means the blog never needs a public domain of its own.
    
        
    
      
    

      
      
    
        
    
          
          08
          
    Point vectore.io at the landing page
            Landing page service › Settings › Networking
          
    
        
    
        
    
          
    Add vectore.io as a custom domain on the landing page service and follow Railway's DNS instructions at your registrar.
    
          
    
            !
            
    The domain goes on the landing page, not the blog. The landing page owns the origin and forwards /blog onward. Pointing the domain at the blog service instead would take the marketing site offline.
    
          
    
          
    Until DNS resolves, the site answers on Railway's generated *.up.railway.app domain — and there it deliberately serves Disallow: /, so a preview URL can never compete with the real one in search. That is expected. Check indexing on the real domain only.
    
        
    
      
    

      
      
    
        
    
          
          09
          
    Run the installer
            vectore.io/blog/wp-admin/
          
    
        
    
        
    
          
    Open https://vectore.io/blog/wp-admin/ and complete the five-field WordPress install. Then:
    
          
    Appearance → Themes — activate Vectore Blog.
    
          
    Appearance → Menus — create a menu and assign it to Header menu, Footer menu, or both. Optional: until you do, the theme falls back to sensible links, so nothing is ever headerless or pointing at a 404.
    
          
    Already done for you: permalinks are set to /%postname%/ and the tagline is filled in, both on first boot. So the very first URL a crawler sees is already the permanent one, rather than ?p=1 being indexed and later redirected.
    
          
    Give yourself a bio under Users → Profile. It turns on the author card at the foot of every post and makes your author page an indexed entity rather than a duplicate post list — which is one of the few signals an AI answer engine can use to weigh a claim.

    If something breaks
    
    
    The five failure modes this setup actually has, and what each one really means.
    
    
    

      
    
        Railway says the deploy failed, but the site loads fine
        
    
          
    The health check is not answering. It must be /blog/healthz, with the prefix — a bare /healthz falls through to WordPress, which returns its 404, and Railway reads any non-2xx as a failed deploy.
    
          
    Check Settings → Deploy → Health Check Path matches what blog/railway.json declares.
    
        
    
      
    

      
    
        wp-admin redirects forever and never loads
        
    
          
    WordPress thinks the visitor is on plain HTTP and keeps redirecting to HTTPS. It is reading X-Forwarded-Proto, which arrives as a list (https,http) because two proxies sit in front of it.
    
          
    The container already reads the leftmost value. If this appears, confirm the landing page is still forwarding the header — that is xfwd in server.js.
    
        
    
      
    

      
    
        The blog homepage works but every post 404s
        
    
          
    Apache is not letting WordPress's .htaccess take over, so nothing is rewriting pretty permalinks. This is the classic symptom of AllowOverride being off, or of RewriteBase losing its /blog prefix.
    
          
    In WordPress, re-save Settings → Permalinks once. If that does not fix it, the build did not pick up the shipped .htaccess.
    
        
    
      
    

      
    
        Uploaded images vanish after a deploy
        
    
          
    The volume is missing or mounted at the wrong path. It must be exactly /var/www/html/wp-content/uploads.
    
          
    Files uploaded before the volume existed are gone for good — re-upload them after fixing the mount.
    
        
    
      
    

      
    
        vectore.io/blog returns the landing page's 404
        
    
          
    BLOG_ORIGIN is unset or wrong on the landing page service, so the proxy never mounted and /blog is just an unknown path.
    
          
    This is deliberate behaviour, not a crash: the landing page runs perfectly well on its own without the blog. Check step 7 and redeploy the landing page.
